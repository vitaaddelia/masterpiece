ACCESSIBILITY · 3 MIN READ

Accessible color is a system decision, not a final check

By Vita Addelia, Product Designer

In 2023 I wrote about checking designs in grayscale so they work for people with color vision deficiency. It is still my favorite ten-second test. What changed is where I put the effort: accessible color works best when it is built into the design system and checked automatically, not fixed screen by screen at the end.

Color vision deficiency affects about 1 in 12 men and 1 in 200 women. On any product with real traffic, that is a lot of people.

The grayscale test still earns its place

Turn on a grayscale filter in your design tool or operating system and look at the screen. Can you still tell an error from a success state? Can you find the primary button? If the answer depends on hue, the design depends on hue, and some people will miss it.

Never let color carry meaning alone

WCAG success criterion 1.4.1 says color must not be the only way to convey information. In practice:

  • Status labels pair color with a word or an icon: "Paid", "Pending", "Disputed".
  • Charts label their series directly or use patterns, so a legend is not the only key.
  • Links in body text are underlined, not just colored.
  • Form errors show a message next to the field, not only a red border.

Contrast is measurable, so measure it

WCAG level AA asks for a contrast ratio of at least 4.5:1 for body text, and 3:1 for large text and for interface parts such as input borders and icons. These are numbers, not opinions. On this portfolio, every text and background pair measures 6:1 or better, which I checked with a script rather than by eye.

Put it in the design system

I have built design systems with Figma Variables across multiple modules of a healthcare ERP, and reusable component libraries across e-commerce client projects. The lesson from both: decide accessibility once, at the token level. Define color tokens as approved pairs (this text color on this surface), give every status token a matching icon and label, and the components inherit the right answer everywhere.

Then check it on every release

The same thinking drives my QA automation work: 413 automated tests across more than 200 pages, run with one API call after every deployment. If a rule matters, check it every time something ships, not once before launch. Accessibility rules are exactly that kind of rule.

Review checklist

  • Does the screen still make sense in grayscale?
  • Is every status, error and chart readable without color?
  • Does body text reach 4.5:1, and do interface parts reach 3:1?
  • Do the tokens encode these rules, so new screens get them for free?
  • Is there an automated check, so the rules survive the next release?
